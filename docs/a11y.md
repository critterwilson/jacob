# Accessibility (T62)

## What v1 ships

* **Skip-to-content link** in the root layout. `sr-only`
  off-focus, visible on focus, jumps to `#main`. Pages that mount
  a `<main id="main">` benefit automatically.
* **Chat message log** is `role="log"` + `aria-live="polite"` so
  screen readers announce new messages without interrupting the
  user. Default `aria-relevant="additions"` keeps deletes/edits
  silent.
* **`<html lang="en">`** is set in the root layout. T61's i18n
  foundation will swap this per active locale when URL routing
  lands.
* **Reduced-motion respect** via `usePrefersReducedMotion()` in
  `lib/a11y.ts`. Components hide non-essential animations
  (typing-indicator pulse, reaction micro-anims) when set.
* **Focus trap helper** at `useFocusTrap()` for modals + pickers.
* **Incident banner** is `role="alert"` + `aria-live="assertive"`
  (existing T59 implementation).
* **Typing indicator** is `aria-live="polite"` + `aria-atomic="true"`
  (existing T48 implementation).
* **All interactive controls have visible labels** — every
  `<button>` has text or an explicit `aria-label`; reactions /
  pinned-message buttons in `MessageItem.tsx` already do this.

## What v1 doesn't ship (deferred follow-ups)

* **`axe-core` CI gate**. The spec calls for an axe-core integration
  test that fails CI on `serious` / `critical` violations. v1
  ships the framework + helpers; the test wiring is a follow-up
  PR (axe-core needs jsdom + a real DOM render of the page tree,
  which the M6 client surfaces are still being audited for).
* **Screen-reader recording** (VoiceOver / NVDA proof). Spec calls
  for video evidence in the PR; manual QA still required.
* **Switch-control demo**. Same — manual QA.
* **WCAG AAA contrast** — we target AA. Existing design tokens
  pass AA on the colours we use; AAA is overshooting for v1.
* **Per-page `<main>` adoption.** The skip link is wired but only
  pages that actually render `<main id="main">` benefit. We've
  added it to a couple of new pages (events, devotionals); the
  rest is incremental.

## Manual a11y checklist for new pages

When you add a new page or surface, run through:

1. **Keyboard nav.** Tab through every interactive element. Tab
   order should match the visual reading order. No focus traps
   except inside modals.
2. **Screen reader.** Open with VoiceOver (Cmd-F5) on macOS or
   NVDA on Windows. Every button should announce its label;
   every section should have a heading.
3. **Reduced motion.** System Preferences → Accessibility →
   Display → Reduce Motion. Confirm no flashing / parallax /
   continuous animation.
4. **Color contrast.** Stark or the Lighthouse a11y audit for a
   spot check. Target WCAG AA (4.5:1 body text, 3:1 large text).
5. **`role="log"`** for any feed-like surface; `role="alert"`
   for things that interrupt; `role="status"` for ambient state.

## What we monitor

Sentry's frontend transactions catch JS errors in screen-reader
flows the same as any other browser — there's no separate "a11y
errors" bucket. If a screen-reader user reports something we'd
want to add as a regression test, capture the URL + steps and
file under the `a11y` label in the issue tracker.
