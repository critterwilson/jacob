# i18n (T61)

## What v1 ships

* English + Spanish message catalogs at
  `frontend/lib/i18n/messages/{en,es}.json`.
* `t(locale, key, vars?)` pure helper + `useT()` React hook.
* `LocaleProvider` for wiring the active locale into the tree.
* `users/{uid}.locale` field round-trips through
  `PATCH /api/users/me` (regex `^[a-z]{2}(?:-[A-Z]{2})?$`).
* T51 streak math already consumes `users/{uid}.locale`.

About 60 keys are translated in both languages — the load-bearing
nav, common chrome, onboarding, settings, events, devotionals.
Everything else falls back to the English string in the same
table; missing keys fall back to the raw key.

## What v1 does NOT ship

* **URL-prefix routing** (`/en/...`, `/es/...`). Spec calls for
  `next-intl`-style routes; that requires restructuring every
  `app/` page tree. Out of scope. The locale resolves from
  `users/{uid}.locale` only in v1.
* **`Accept-Language` header detection** (server components).
  Documented as the next layer, not implemented.
* **RTL support** (Arabic, Hebrew). The spec calls for tailwind
  `dir-rtl:` scaffolding; v1 doesn't add the variant utility,
  but the `t()` API has no RTL coupling so when a Phase 4 RTL
  locale lands the string lookup is already in place.
* **Email template translation.** The current backend templates
  are English-only. The architecture is in place
  (`backend/app/services/email.py` could pick a template by
  locale) but we don't ship `*.es.html.j2` files yet — the
  templates are small enough that human translation is the
  follow-up step.

## Adding a string

1. Add the key to `en.json`. Use dot-notation:
   `nav.groups`, `events.checkIn.notOpen`, etc.
2. Add the same key to `es.json`. If you don't have a translation,
   skip it — the resolver falls back to English. Consider opening
   a follow-up issue.
3. Use `useT()` in the component:

   ```tsx
   import { useT } from "@/lib/i18n";

   function Nav() {
     const t = useT();
     return <a href="/groups">{t("nav.groups")}</a>;
   }
   ```

## Adding a locale

1. Drop a new `frontend/lib/i18n/messages/<code>.json` with at
   minimum the keys present in `en.json`.
2. Append the code to `SUPPORTED_LOCALES` in
   `frontend/lib/i18n/index.tsx`.
3. Add a tz mapping to `_LOCALE_TZ` in
   `backend/app/services/devotionals.py` so streak math knows the
   right day boundary. (Default is UTC; that works for any locale
   where the user is roughly within a few hours of UTC, but a
   real mapping is the correct call.)
4. If the locale is RTL: add the tailwind `dir-rtl:` variant
   utility class scaffolding (Phase 4 work).

## Pluralization

Not yet supported. The current resolver does string interpolation
only (`{streak}` → "5"). When we need plural rules ("1 day streak"
vs. "5 day streak"), wire `Intl.PluralRules` in.

## Date / time formatting

Use `new Date(value).toLocaleString(locale, { dateStyle: "medium" })`
at the call site. Don't hard-code formatting helpers — the user's
locale lives in `LocaleProvider`.
